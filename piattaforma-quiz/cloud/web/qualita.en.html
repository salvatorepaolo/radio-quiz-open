Software quality and security

radio-quiz.it · ← Back to Radiology Quiz · Italiano

This page explains how we protect data, how we check that cases and their scoring are correct, and how we test the software before every release. The checks described here are automatic and run again at every change: they are not promises, but tests the software must pass before it goes online.

Educational tool, not a medical device. Radiology Quiz is for training on anonymous cases. It is not certified as a medical device and must not be used for diagnosis, reporting or clinical decisions. The checks on this page concern educational correctness, privacy and software security, not clinical use.

  • 🔒 Data that stays putImages are anonymized before publication; the desktop viewer makes no network requests, and a test checks it.
  • ✅ Every case re-scoredAt every change, the scoring of all cases is recalculated with typical answers and compared with the expected one.
  • 🚦 Release blockedIf even one check fails, the site is not updated.
  • 🔓 All open sourceSoftware, AI models and testing tools are open source, with checked licenses. The platform's source code is public (EUPL 1.2 licence): github.com/salvatorepaolo/radio-quiz-open.

1. Privacy by design

Case images

  • Allow-list anonymization. Only the technical DICOM fields needed to view and measure the image are kept. Everything else is removed: name, IDs, address, physicians, institution, manufacturers' private fields. Dates are reduced to month and year and identifiers (UIDs) are regenerated.
  • Text burned into the image. A text-recognition (OCR) check looks for names and dates written in the pixels. The areas found are covered in the pixels themselves, before the file leaves the computer.
  • Ultrasound. Only the inside of the image regions declared by the scanner is kept; everything else, where the device writes name, institution and date, is blacked out.
  • Cautious exclusions. Images that cannot be anonymized with certainty are not published: summary screenshots, structured reports, “secondary capture” and “for processing” images. Original reports are never uploaded.
  • Check after anonymization. Every file produced is read again, looking for the patient's words and for suspicious fields. Before a case is made visible, the headers of all its images and a sample of the pixels are checked again.

The desktop viewer

  • Files opened in the client viewer stay on the computer: they are not sent to the site or to any other service.
  • An automatic test opens the viewer in a real browser and checks that no network request is made while it is used.
  • Files a teacher prepares for a new case are anonymized in the browser: patient data never leaves the computer.

Artificial intelligence

  • Only open-source models are used, running in the browser or offline on cases that are already anonymous. No image is sent to external AI services.

How we test it

With synthetic DICOM files containing invented data (never real data). The tests check, searching the file's raw bytes too:

  • that no patient data survives;
  • that pixels and technical fields stay identical;
  • that burned-in text is covered, in compressed images too, without the original pixels remaining in the file;
  • that in ultrasound everything outside the image regions turns black;
  • that anonymization in the browser and on the preparation computer produce the same identifiers.

At every change, a thousand randomly generated files are added, with invented data in ever-different fields and formats, plus deliberately damaged files (truncated or with altered bytes). No patient data may get through in any of them. This test has already closed two gaps that hand-written tests did not see: a file with a wrong length could hide the name inside a technical field, and a free-comment field among the technical ones stayed in the file. A malformed file is now excluded.

2. Correct cases and scoring

  • Every case re-scored at every change. For each of the more than 130 cases a test simulates typical answers. It checks that:
    • all the correct answers score 100 and no answer scores 0;
    • choosing a distractor lowers the score;
    • a report with the expected findings passes and one with wrong statements does not;
    • communicating the result as expected scores 100;
    • a mark placed on the centre of the finding counts as “on target”.
    Every score is then compared with the stored one: if a change to the case or to the code alters it, the test says which case and which answer.
  • Scales and classifications. The clinical scales used in the cases are tested with example cases and about 4,000 combinations, compared with the expected results.
  • Complete cases. No visible case may contain text still “to be filled in” or lack correct answers.
  • Analyses for teachers. The calculations are tested on an invented class, with expected values worked out by hand: option discrimination, missed secondary findings, calibration of stated confidence, error map.

4. Code quality

  • Checks before every change. Before a change enters the code repository, an automatic check makes sure it does not contain:
    • passwords, keys or tokens;
    • DICOM files, recognized even when renamed: images never enter the code repository;
    • programming errors (ESLint);
    • script errors (ShellCheck).
    The fast tests run too.
  • Tests repeated on an independent server. At every change the same checks, and all the tests that do not need the case images, run again on a GitHub server, starting from a clean copy.
  • Test coverage. We measure which lines of code are executed by the tests: today 86% of the modules tested without a browser (scoring, anonymization, reports, analyses, scales, server) and about half of the viewer, measured in the browser during the tests. The least covered parts are the first candidates for new tests.
  • No secrets in the code. The whole history of the repository has been checked: no key or password appears in it.
  • Two copies of the repository, on two different services, as a backup.

5. Security

  • Passwords. They are stored only as a hash (scrypt with salt) and must have at least 10 characters, with letters and a number or symbol. After 5 wrong attempts access is blocked for 15 minutes.
  • Links sent by email. They are single-use and expire: confirmation after 48 hours, password change after one hour. Registration, confirmation, password reset and the lockout after wrong attempts are tested at every change by following the links as a person would. An address that is already registered gets the same reply as a new one, so nobody can find out who is registered.
  • Sessions. They use a protected technical cookie (HttpOnly, Secure, SameSite). A password change closes the other sessions.
  • Permissions, tested at every release.
    • A student does not receive the solution, notes or internal title of a case before answering.
    • The score is calculated by the server.
    • A teacher only sees the students who chose them.
    • A case's images open only after the case has been opened.
  • Page protected by the browser. The content security policy (CSP) forbids scripts inserted into the page and third-party scripts. The security headers (HSTS, protection against framing, no access to camera and location) are active. A test checks that no inserted script appears in the page.
  • User text. What you write in the report stays text: the tests check that it cannot become code in the page, the PDF or the Word file.
  • Data retention, checked by tests. Registrations never confirmed are deleted after a week. An account inactive for 24 months is deleted only after a notice sent a month earlier, and its answers remain only in anonymous form. On company platforms the administrator decides.
  • User rights, checked by tests. “Download my data” produces a file with profile and answers, without password hashes or tokens. Deleting the account requires the password, makes the answers anonymous and removes the person from those who had chosen them as a teacher.
  • No third-party tracking. Only technical cookies.

6. How a new version is released

  1. Changes pass the automatic checks before entering the code repository; then the tests run again on GitHub.
  2. The release runs all the tests again: if a single one fails, it stops and the site stays as it was.
  3. The site's files are minified, checked again and uploaded; every version has a sequential number.
  4. Right afterwards, a check on the real site verifies access, permissions and images.

7. Known limitations

  • The tests use invented data and cases from public archives: they show that the software behaves as intended in those situations, not that it is free of errors.
  • About half of the viewer code is not yet touched by any automatic test: coverage is being extended step by step, starting from the most delicate parts.
  • Automatic accessibility checks do not replace testing with people who use assistive technologies.
  • AI suggestions and corrections can be wrong: always check them with your own reading.
  • Automatic anonymization greatly reduces the risk but does not eliminate it: this is why a case becomes visible only after the checks described above and the administrator's decision.

9. Reporting problems

Found an error in a case, a security problem or data that should not be there? Write to info@radio-quiz.it; for privacy, to privacy@radio-quiz.it. Security reports are handled with priority: please do not disclose them before the problem is fixed.
